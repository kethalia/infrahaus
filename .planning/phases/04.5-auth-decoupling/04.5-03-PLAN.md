**Refactor `apps/dashboard/src/lib/containers/helpers.ts`:**

This is the most important change in this plan. Currently `createSessionClient` uses `getProxmoxCredentials()` (which extracted a Proxmox session ticket from the session). After migration, the session has NO Proxmox ticket. Proxmox API auth comes from the node's stored API token.

1. **Remove** `import { getProxmoxCredentials } from "@/lib/session"`
2. **Add** `import { getSessionData } from "@/lib/session"`
3. **Add** `import { createProxmoxClientFromNode } from "@/lib/proxmox/index"`
4. **Add** `import type { ProxmoxNode } from "@/generated/prisma/client"` (already imported)

5. **Rewrite `createSessionClient()`:**
   ```typescript
   /**
    * Create an authenticated ProxmoxClient using the node's stored API token
    * credentials. Verifies the user is authenticated via session check.
    *
    * Use this for all interactive Proxmox calls (RSC, server actions).
    * Node credentials (API token) provide Proxmox API access.
    * Session check ensures the user is authenticated (wallet connected).
    *
    * @param node - ProxmoxNode from database (must have tokenId + tokenSecret)
    * @returns ProxmoxClient authenticated with node's API token
    * @throws ActionError if session is invalid or node has no API token
    */
   export async function createSessionClient(
     node: Pick<ProxmoxNode, "host" | "port" | "tokenId" | "tokenSecret" | "name">,
   ): Promise<ProxmoxClient> {
     const sessionData = await getSessionData();
     if (!sessionData) {
       throw new ActionError("Not authenticated. Connect your Universal Profile.");
     }

     return createProxmoxClientFromNode(node as ProxmoxNode);
   }
   ```
   Note: `createProxmoxClientFromNode` already throws a clear error if tokenId/tokenSecret are null ("Node X does not have API token credentials configured. Add them in Settings → Nodes."). No need to duplicate that check.

   The parameter type change from `Pick<ProxmoxNode, "host" | "port">` to include `"tokenId" | "tokenSecret" | "name"` is safe — ALL callers already pass full ProxmoxNode objects from DatabaseService queries. TypeScript will verify this at build time.

6. **Remove `createProxmoxClientFromSession()`** — it's dead code (grep confirms it's only defined, never called from outside helpers.ts)

7. **Update module JSDoc** to reflect the new auth model:
   ```
   * Container helpers — server-only utilities for container management.
   *
   * Provides reusable patterns for getting authenticated ProxmoxClient
   * from node-stored API token credentials. Session check ensures the
   * user is authenticated (Universal Profile connected).
   *
   * The worker process uses createProxmoxClientFromNode() directly (no session).
   ```

  <name>Task 3: ProxmoxNode userId data migration</name>
  <files>
    apps/dashboard/prisma/migrations/
  </files>
  <action>
**Context:** The `ProxmoxNode.userId` column currently stores Proxmox usernames (e.g., `root@pam`). After auth migration, new sessions store Universal Profile addresses (e.g., `0x1234...abcd`). Existing node rows will be orphaned because `listNodesForUser('0x1234...')` won't match `userId = 'root@pam'`.

**Solution:** Create a Prisma migration that clears existing ProxmoxNode data. This is a personal development tool — the user will re-add their nodes after connecting their Universal Profile for the first time. This is the intended UX per CONTEXT.md: "No-nodes state becomes the real first-login experience."

1. **Create the migration:**
   ```bash
   npx prisma migrate dev --create-only --name auth_decoupling_clear_nodes
   ```

2. **Edit the generated migration SQL** to add:
   ```sql
   -- Auth decoupling: Clear ProxmoxNode records with Proxmox username userId values.
   -- After this migration, users log in via Universal Profile (wallet address).
   -- Existing nodes stored under Proxmox usernames (e.g., 'root@pam') become
   -- unreachable since the new userId format is a wallet address (e.g., '0x1234...').
   -- Users will re-add their Proxmox nodes in Settings after first UP login.
   DELETE FROM "ProxmoxNode";
   ```

3. **Apply the migration:**
   ```bash
   npx prisma migrate dev
   ```

**Why DELETE instead of UPDATE:** We can't know the user's wallet address at migration time (they haven't logged in with their UP yet). The `DELETE` approach is clean — when they first log in with their UP, the dashboard shows the "No nodes configured" banner guiding them to Settings → Nodes. This is the exact first-login experience described in CONTEXT.md.

**Why not skip this:** Without clearing old data, the database accumulates orphaned records. While functionally harmless (they're just invisible), it's dirty data that could cause confusion during debugging.

**Alternative for users who want to preserve node data:** They can skip this migration and instead run a manual UPDATE after their first UP login:
```sql
UPDATE "ProxmoxNode" SET "userId" = '0xYourWalletAddress' WHERE "userId" = 'root@pam';
```
Document this alternative in the migration file as a SQL comment.
  </action>

  </verify>
