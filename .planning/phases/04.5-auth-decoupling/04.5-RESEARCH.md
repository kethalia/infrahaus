# Phase 04.5: Auth Decoupling — RainbowKit + Universal Profiles - Research

**Researched:** 2026-02-23
**Domain:** Web3 wallet authentication (SIWE + RainbowKit + LUKSO Universal Profiles)
**Confidence:** HIGH

## Summary

This phase replaces the current Proxmox-coupled authentication with Web3 wallet authentication using RainbowKit, restricted to LUKSO Universal Profiles only. Users connect their Universal Profile, sign a SIWE (Sign-In with Ethereum) message, and the server verifies the signature to create a session in Redis (same iron-session + Redis architecture, different payload).

The standard approach is well-established: RainbowKit v2.2.9+ has a **built-in `universalProfilesWallet` connector**, and LUKSO's chain (`lukso`) is already available in `viem/chains` and `wagmi/chains`. The SIWE flow uses `viem/siwe` utilities for message creation, parsing, and verification. RainbowKit's `createAuthenticationAdapter` + `RainbowKitAuthenticationProvider` pattern handles the client-side SIWE flow, while server-side verification happens in Next.js API routes.

The critical technical consideration is that Universal Profiles are **smart contract accounts** (not EOAs), so signature verification must use EIP-1271 (`isValidSignature`). Viem's `verifySiweMessage` handles this automatically by detecting smart contract signers.

**Primary recommendation:** Use RainbowKit v2.2.10 with built-in `universalProfilesWallet`, `viem/siwe` for SIWE utilities, custom authentication adapter (not the NextAuth integration), and App Router API routes for nonce/verify/logout endpoints. Keep the existing iron-session + Redis architecture with a modified session payload.

### Pattern 2: Custom Authentication Adapter (SIWE + iron-session)
**What:** RainbowKit's `createAuthenticationAdapter` to connect wallet connection with SIWE auth
**When to use:** In the client-side provider wrapper
**Example:**
```typescript
// Source: RainbowKit custom authentication docs + iron-session example
// src/components/providers/web3-provider.tsx
"use client";

import { createAuthenticationAdapter, RainbowKitAuthenticationProvider } from '@rainbow-me/rainbowkit';
import { createSiweMessage } from 'viem/siwe';

const authAdapter = createAuthenticationAdapter({
  getNonce: async () => {
    const response = await fetch('/api/auth/nonce');
    return await response.text();
  },
  createMessage: ({ nonce, address, chainId }) => {
    return createSiweMessage({
      domain: window.location.host,
      address,
      statement: 'Sign in to LXC Manager with your Universal Profile.',
      uri: window.location.origin,
      version: '1',
      chainId,
      nonce,
      expirationTime: new Date(Date.now() + 2 * 60 * 60 * 1000), // 2 hours
    });
  },
  verify: async ({ message, signature }) => {
    const response = await fetch('/api/auth/verify', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ message, signature }),
    });
    return Boolean(response.ok);
  },
  signOut: async () => {
    await fetch('/api/auth/logout', { method: 'POST' });
  },
});
```

### Pattern 3: Server-Side SIWE Verification (API Route)
**What:** Verify SIWE signature server-side, create Redis session
**When to use:** `/api/auth/verify` route handler
**Example:**
```typescript
// Source: viem/siwe docs + RainbowKit iron-session example (adapted for App Router)
// src/app/api/auth/verify/route.ts
import { NextResponse } from 'next/server';
import { createPublicClient, http } from 'viem';
import { lukso } from 'viem/chains';
import { parseSiweMessage, type SiweMessage } from 'viem/siwe';
import { createSession } from '@/lib/session';

const publicClient = createPublicClient({
  chain: lukso,
  transport: http('https://42.rpc.thirdweb.com'),
});

export async function POST(request: Request) {
  const { message, signature } = await request.json();
  const siweMessage = parseSiweMessage(message) as SiweMessage;

  // verifySiweMessage handles EIP-1271 for smart contract accounts (Universal Profiles)
  const valid = await publicClient.verifySiweMessage({
    message,
    signature,
    // nonce could be verified here too, or separately
  });

  if (!valid) {
    return NextResponse.json({ ok: false }, { status: 401 });
  }

  // Verify nonce matches stored nonce (from /api/auth/nonce)
  // ... nonce verification logic ...

  // Create session with SIWE data
  const messageHash = ''; // keccak256 of the message
  const expiresAt = siweMessage.expirationTime?.toISOString()
    ?? new Date(Date.now() + 2 * 60 * 60 * 1000).toISOString();

  await createSession({
    address: siweMessage.address!,
    signature,
    message,
    messageHash,
    expiresAt,
  });

  return NextResponse.json({ ok: true });
}
```

### Anti-Patterns to Avoid
- **Don't use `@rainbow-me/rainbowkit-siwe-next-auth`:** This is for NextAuth, not custom auth. Use `createAuthenticationAdapter` + `RainbowKitAuthenticationProvider` instead.
- **Don't verify SIWE in server actions:** SIWE verification requires `publicClient.verifySiweMessage()` which makes an RPC call. Use API routes (`route.ts`) for this. Server actions can't handle the initial unauthenticated SIWE flow anyway (loginAction pattern uses `actionClient`, but the wallet connect + sign flow is client-initiated).
- **Don't store nonce in Redis with a separate key:** Use the iron-session cookie to store the nonce temporarily during the SIWE flow. The nonce only needs to survive the few seconds between `/api/auth/nonce` and `/api/auth/verify`.
- **Don't use `publicClient.verifyMessage()`:** Use `publicClient.verifySiweMessage()` which validates SIWE fields (domain, nonce, expiry) AND verifies the signature (including EIP-1271 for smart contracts).
- **Don't install wagmi v3:** RainbowKit 2.2.10 requires `wagmi ^2.9.0`. wagmi v3 is NOT compatible.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| SIWE message formatting | Custom string templating | `createSiweMessage` from `viem/siwe` | EIP-4361 has strict format requirements |
| Nonce generation | `Math.random()` or `crypto.randomUUID()` | `generateSiweNonce` from `viem/siwe` | Produces compliant random alphanumeric nonce |
| SIWE message parsing | Regex parsing | `parseSiweMessage` from `viem/siwe` | Handles all edge cases in EIP-4361 format |
| Smart contract signature verification | Manual `isValidSignature` call | `verifySiweMessage` from viem | Automatically detects EOA vs contract, uses EIP-1271 for contracts |
| Wallet connection UI | Custom modal | RainbowKit `ConnectButton` | Handles connection states, error handling, wallet switching |
| Universal Profile connector | Custom EIP-6963 provider discovery | `universalProfilesWallet` from `@rainbow-me/rainbowkit/wallets` | Official connector since RainbowKit v2.2.9, handles both browser extension and mobile app |
| LUKSO chain definition | Custom `defineChain()` | `lukso` from `viem/chains` / `wagmi/chains` | Pre-configured with correct chainId (42), RPC URLs, block explorer |
| Authentication state management | Custom React context | `RainbowKitAuthenticationProvider` with `AuthenticationStatus` | Handles loading/authenticated/unauthenticated states, integrates with ConnectButton |

**Key insight:** The entire SIWE + wallet connect + session management flow is well-served by existing libraries. The only custom code needed is: (1) API route handlers for nonce/verify/logout, (2) session creation/destruction using existing iron-session + Redis pattern, (3) the authentication adapter configuration.

## Common Pitfalls

### Pitfall 1: EIP-1271 Verification for Universal Profiles
**What goes wrong:** Using standard ECDSA `ecrecover` to verify SIWE signatures from Universal Profiles fails because UPs are smart contracts, not EOAs. The signing is done by a controller key, not the UP address itself.
**Why it happens:** Universal Profiles use EIP-1271 (`isValidSignature`) for signature verification. The controller key signs the message, and the UP smart contract validates the controller has `SIGN` permission.
**How to avoid:** Use `publicClient.verifySiweMessage()` from viem, which automatically detects smart contract accounts and calls `isValidSignature`. This requires an RPC connection to LUKSO mainnet.
**Warning signs:** Signature verification returns `false` for every attempt, even with a valid signature.

### Pitfall 2: Nonce Storage Race Condition
**What goes wrong:** If the nonce is stored in a separate Redis key and multiple browser tabs are open, the nonce from one tab can overwrite another's.
**Why it happens:** Each `/api/auth/nonce` call generates a new nonce. If the user has multiple tabs, only the last nonce is valid.
**How to avoid:** Store the nonce in the iron-session cookie itself (not Redis). Each browser session gets its own cookie, so each tab's nonce is independent. The verify endpoint reads the nonce from the same cookie.
**Warning signs:** "Invalid nonce" errors when the user has multiple tabs.

### Pitfall 3: Turbopack Compatibility
**What goes wrong:** RainbowKit or wagmi may require webpack-specific features that Turbopack doesn't support.
**Why it happens:** RainbowKit uses `@vanilla-extract/css` internally. Some older versions had Turbopack issues.
**How to avoid:** RainbowKit 2.2.10 explicitly supports Turbopack (per official docs: "RainbowKit works with both Turbopack and webpack"). If issues arise, the fallback is adding `--webpack` flag to dev/build scripts. The project's `next.config.ts` already has Turbopack config.
**Warning signs:** CSS not loading, build errors related to `@vanilla-extract`.

### Pitfall 4: WalletConnect Project ID Required
**What goes wrong:** RainbowKit fails to initialize if no WalletConnect `projectId` is provided.
**Why it happens:** `connectorsForWallets` requires a projectId for WalletConnect-based connections (the UP mobile app uses WalletConnect under the hood).
**How to avoid:** Create a free project ID at https://cloud.walletconnect.com/ and set it as `NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID` env var.
**Warning signs:** Console error about missing projectId, wallet connection modal doesn't appear.

### Pitfall 5: SSR Hydration Mismatch
**What goes wrong:** React hydration errors because wallet state differs between server and client.
**Why it happens:** Wallet connection state only exists on the client. If the provider renders wallet-dependent content during SSR, it mismatches.
**How to avoid:** Set `ssr: true` in wagmi `createConfig`. Ensure the `Web3Provider` is a `"use client"` component. Use `useAccount()` only in client components.
**Warning signs:** React hydration mismatch warnings in console.

### Pitfall 6: Session Cookie for Both Nonce and Session
**What goes wrong:** The iron-session cookie is overwritten when creating the session, losing the nonce validation.
**Why it happens:** The project uses iron-session with a single cookie. The nonce is stored in the same cookie as the session.
**How to avoid:** The verify endpoint should: (1) read the nonce from the cookie, (2) validate it, (3) THEN overwrite the cookie with the session data. Since both happen in the same request, the nonce is verified before being replaced.
**Warning signs:** N/A — just ensure the verify endpoint reads nonce before creating session.

### Pitfall 7: `viem` Version Compatibility
**What goes wrong:** Build errors or runtime crashes from viem version mismatch.
**Why it happens:** The project already has `viem@2.x` as a wagmi dependency. RainbowKit also needs `viem 2.x`. Conflicts can arise if multiple viem versions are installed.
**How to avoid:** Don't pin a specific viem version — let it be resolved by the wagmi/RainbowKit peer dependency. Check `pnpm ls viem` to ensure only one version is installed.
**Warning signs:** Type errors, duplicate module warnings.

### Pitfall 8: Auth Status Polling vs. Static Check
**What goes wrong:** The authentication status (`loading`/`authenticated`/`unauthenticated`) gets stale if the session expires server-side.
**Why it happens:** RainbowKit needs to know the auth status on the client, but sessions live on the server.
**How to avoid:** Add a `/api/auth/me` endpoint that returns session status. Poll it on page load and window focus (see RainbowKit iron-session example). The adapter's `verify` callback sets status to `authenticated` on success.
**Warning signs:** User appears connected but API calls fail with auth errors.

### Verify API Route (App Router)
```typescript
// Source: RainbowKit iron-session example + viem SIWE docs (adapted)
// src/app/api/auth/verify/route.ts
import { NextResponse } from 'next/server';
import { createPublicClient, http, keccak256, toHex } from 'viem';
import { lukso } from 'viem/chains';
import { parseSiweMessage, type SiweMessage } from 'viem/siwe';
import { getSession, createSession } from '@/lib/session';

const publicClient = createPublicClient({
  chain: lukso,
  transport: http('https://42.rpc.thirdweb.com'),
});

export async function POST(request: Request) {
  try {
    const { message, signature } = await request.json();

    // Parse the SIWE message to extract fields
    const siweMessage = parseSiweMessage(message) as SiweMessage;

    // Verify nonce matches what was issued
    const session = await getSession();
    if (siweMessage.nonce !== session.nonce) {
      return NextResponse.json({ message: 'Invalid nonce' }, { status: 422 });
    }

    // Verify signature (handles EIP-1271 for Universal Profiles automatically)
    const valid = await publicClient.verifySiweMessage({
      message,
      signature,
    });

    if (!valid) {
      return NextResponse.json({ ok: false }, { status: 401 });
    }

    // Compute message hash
    const messageHash = keccak256(toHex(message));

    // Calculate TTL from SIWE expirationTime
    const expiresAt = siweMessage.expirationTime?.toISOString()
      ?? new Date(Date.now() + 2 * 60 * 60 * 1000).toISOString();

    // Create session in Redis
    await createSession({
      address: siweMessage.address!,
      signature,
      message,
      messageHash,
      expiresAt,
    });

    return NextResponse.json({ ok: true });
  } catch (error) {
    console.error('[auth] SIWE verification failed:', error);
    return NextResponse.json({ ok: false }, { status: 500 });
  }
}
```

## Migration Strategy

### userId Column Migration
The `ProxmoxNode.userId` column currently stores Proxmox usernames (e.g., `root@pam`). After migration, it stores Universal Profile addresses (e.g., `0x1234...abcd`).

**Approach:** Since this is a development/personal tool (not a multi-tenant production app), the simplest approach is:

1. **Schema stays the same** — `userId String` column is already a string, no schema migration needed
2. **Data migration** — Create a Prisma migration script or manual SQL to update existing rows. Since this is a personal tool, the existing data can simply be cleared or manually updated
3. **No downtime concern** — This is a development tool, not a production SaaS

**If data preservation is important:**
```sql
-- Manual migration (run once after deployment)
-- Option A: Clear all nodes (user re-adds them with UP credentials)
DELETE FROM "ProxmoxNode";

-- Option B: Update userId for known mapping (if migrating a specific user)
UPDATE "ProxmoxNode" SET "userId" = '0xNewAddress...' WHERE "userId" = 'root@pam';
```

```typescript
// This stays exactly the same — Edge compatible
const sessionCookie = request.cookies.get(SESSION_COOKIE_NAME);

  return NextResponse.redirect(new URL("/login", request.url));
}
```

## Open Questions

1. **Nonce storage approach**
   - What we know: The RainbowKit iron-session example stores nonce in the iron-session cookie. Our current session architecture puts session data in Redis and only the session ID in the cookie.
   - What's unclear: Should the nonce go in the iron-session cookie directly (simpler, per-browser), or in Redis keyed by a temporary session ID?
   - Recommendation: Store nonce in iron-session cookie directly. During the nonce→verify flow, there's no "session" yet. The cookie is the perfect temporary storage. After verify succeeds, the cookie gets the real session ID.

2. **Session TTL calculation from SIWE `expirationTime`**
   - What we know: The user's CONTEXT.md specifies "session expiry derived from the SIWE message's `expirationTime` field." The `createSiweMessage` can include an `expirationTime` parameter.
   - What's unclear: Who sets the expirationTime — the client (in `createMessage`) or does the server enforce a max?
   - Recommendation: The client sets `expirationTime` in `createMessage` (e.g., 2 hours from now). The server extracts this from the parsed SIWE message and uses it for Redis TTL. The server should enforce a maximum (e.g., cap at 24 hours) regardless of what the client requests.

3. **RainbowKit CSS import location**
   - What we know: RainbowKit requires `import '@rainbow-me/rainbowkit/styles.css'`.
   - What's unclear: Should this go in the root layout, the `Web3Provider` component, or `globals.css`?
   - Recommendation: Import it in the `Web3Provider` client component (where other RainbowKit imports live). This keeps the dependency isolated. It can also go in `globals.css` via `@import`.

4. **`session.nonce` type in iron-session**
   - What we know: The iron-session `SessionData` interface needs to accommodate both the temporary nonce (during auth flow) and the session ID (after auth).
   - Recommendation: Extend the `SessionData` interface: `{ sessionId?: string; nonce?: string; }`. The nonce is set during `/api/auth/nonce`, read during `/api/auth/verify`, then replaced with `sessionId` after successful auth.
