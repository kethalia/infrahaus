# Phase 04.6 Plan 01: Pool-Based Proxmox Access Control Summary

Optional Proxmox resource pool field on ProxmoxNode, threaded end-to-end through node form → create action → BullMQ job → worker → Proxmox API `pool` parameter for per-user container isolation.

## What Was Done

### Task 1: Database Migration
Added `pool String?` column to `ProxmoxNode` model in Prisma schema, positioned after `tokenSecret` and before `fingerprint`. Created manual migration SQL (`ALTER TABLE "ProxmoxNode" ADD COLUMN "pool" TEXT`). Regenerated Prisma client.

### Task 2: Schemas & DB Layer
Added `pool: z.string().optional()` to all three node Zod schemas (`createNodeSchema`, `updateNodeSchema`, `editNodeFormSchema`). Updated `DatabaseService.createNode` and `updateNode` type interfaces to include `pool`. Updated `createNodeAction` to pass `pool` on create and `updateNodeAction` to handle pool updates (empty string clears to null).

### Task 3: Node Form Dialog
Added "Resource Pool" `FormField` to `NodeFormDialog` after the Token Secret field. Default value populated from `node?.pool`. Pool included in both create and update submission payloads. Placeholder: "e.g. infrahaus-alice" with description linking to setup guide.

### Task 4: Creation Pipeline
Added `pool?: string` to `ContainerJobData.config`. `createContainerAction` reads `node.pool` from the DB record and passes it into the job config. Worker passes `config.pool` to `createContainer()` which already appends it to the Proxmox API form data when defined.

### Task 5: Setup Guide
The `proxmox-api-token-setup.md` guide already included the Pool field in Step 5 (dashboard form fill-in). No outdated "planned feature" notes existed. No changes needed.
