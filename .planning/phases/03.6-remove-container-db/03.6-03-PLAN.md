reads from the DB Container or ContainerEvent tables. The dashboard, detail page,
progress page, and all components use Proxmox API + Redis exclusively.

Output: Simplified data layer, Redis-only API routes, vmid-based navigation throughout.

  <name>Task 1: Rewrite data layer to Proxmox-first + Redis creation state</name>
  <files>apps/dashboard/src/lib/containers/data.ts</files>
  <action>
This is the most significant change. The data layer currently merges DB container records
with Proxmox live status. After this change, Proxmox is the sole source of truth,
with Redis providing in-progress creation state.

**Remove imports:**
- Remove `DatabaseService` import (no more DB container queries)
- Remove `ContainerWithRelations`, `ContainerWithDetails`, `ContainerCounts` types from `@/lib/db`
- Remove `type Container` if imported

**Add imports:**
- `import { getRedis } from "@/lib/redis"`
- `import { listActiveCreations, getCreationJob, type CreationJob } from "@/lib/containers/redis-state"`

**Update `ContainerStatus` type:**
Keep as-is: `"running" | "stopped" | "creating" | "error" | "unknown"`

**Update `ContainerWithStatus` interface:**
Remove the `id: string` field (was cuid or pve-{vmid}). Use `vmid: number` as the primary identifier.
The interface should be:
```typescript
export interface ContainerWithStatus {
  vmid: number;
  hostname: string;
  node: { name: string; id: string };
  template: { name: string } | null;
  status: ContainerStatus;
  maxmem?: number;
  maxdisk?: number;
  maxcpu?: number;
  uptime?: number;
  netin?: number;
  netout?: number;
  // Service cache (from Redis)
  services?: CachedServiceInfo[];
  serviceCount?: number;
  containerIp?: string | null;
}
```

**Update `ContainersPageData` interface:**
```typescript
export interface ContainersPageData {
  containers: ContainerWithStatus[];
  counts: { total: number; running: number; stopped: number; creating: number; error: number };
  proxmoxReachable: boolean;
}
```
Note: counts are now computed from the merged list (not from DB aggregate query).

**Rewrite `getContainersWithStatus(userId: string)`:**

New algorithm:
1. Fetch user's DB nodes: `DatabaseService.listNodesForUser(userId)` (ProxmoxNode stays in DB)
2. For each node, fetch Proxmox containers in parallel (same as current step 1)
   - Use `listContainers(client, dbNode.name)` — returns ProxmoxContainerStatus[]
   - Handle per-node errors gracefully (same error isolation pattern)
3. Fetch Redis creation state: `const redis = getRedis(); const activeCreations = await listActiveCreations(redis);`
4. Fetch cached services from Redis for all containers (keyed by String(vmid))
5. Map Proxmox containers to `ContainerWithStatus`:
   ```typescript
   const containers: ContainerWithStatus[] = pveContainers.map(pve => ({
     vmid: pve.vmid,
     hostname: pve.name || `CT-${pve.vmid}`,
     node: { name: pve.nodeName, id: pve.nodeId },
     template: null,  // Template link no longer available (was DB-only)
     status: pve.status as ContainerStatus,
     maxmem: pve.maxmem,
     maxdisk: pve.maxdisk,
     maxcpu: pve.cpus,
     uptime: pve.uptime,
     netin: pve.netin,
     netout: pve.netout,
     // Merge cached services if available
     ...servicesByVmid.get(pve.vmid),
   }));
   ```
6. Add Redis creation state containers not yet visible in Proxmox:
   ```typescript
   const pveVmids = new Set(pveContainers.map(p => p.vmid));
   for (const creation of activeCreations) {
     if (!pveVmids.has(creation.vmid)) {
       containers.push({
         vmid: creation.vmid,
         hostname: creation.hostname,
         node: { name: creation.nodeName, id: creation.nodeId },
         template: null,
         status: creation.lifecycle as ContainerStatus,  // "creating" or "error"
       });
     }
   }
   ```
7. Sort by vmid, compute counts from the list
8. Return `{ containers, counts, proxmoxReachable }`

This is a significant SIMPLIFICATION — the complex DB/Proxmox merge logic, `dbByVmid` map,
and `mergeContainerStatus` helper are all removed.

**Rewrite `getContainerDetailData(containerId: string, userId: string)`:**

The `containerId` parameter is now always a vmid string (e.g., "601").
Remove the DB path entirely. The function becomes essentially the current
`getProxmoxOnlyContainerDetail()` logic:

1. Parse vmid: `const vmid = parseInt(containerId, 10)` — return null if NaN
2. Get user nodes from DB
3. For each node, try to find the container via Proxmox API
4. If found: build detail data with config, services cache, resolved IP
5. If not found on any node: check Redis creation state (`getCreationJob`)
   - If creating/error: return minimal detail data with creation state
   - If not found anywhere: return null
6. Events: Read from Redis log buffer (`getLogBufferKey(containerId)`) for creation events
   - Parse each JSON entry to extract step/log events
   - No DB events (ContainerEvent table no longer queried)

**Remove `mergeContainerStatus()` helper** — no longer needed.
**Remove `getProxmoxOnlyContainerDetail()`** — its logic is now the main path.

**Update `ContainerDetailData` interface:**
```typescript
export interface ContainerDetailData {
  container: ContainerWithStatus & {
    config: ProxmoxContainerConfig | null;
    containerIp: string | null;
    services: CachedServiceInfo[];
  };
  events: Array<{
    type: string;
    message: string;
    timestamp: string;
    metadata?: Record<string, unknown>;
  }>;
}
```
Events come from Redis log buffer (creation events) rather than DB ContainerEvent.

**IMPORTANT:** Keep the `createSessionClient` import from `helpers.ts` — it still uses DB
ProxmoxNode records for host/port. Node operations stay in DB.

**SSE Progress Route (`progress/route.ts`):**

Currently the route:
1. Looks up container in DB via `DatabaseService.getContainerById(containerId)`
2. Fetches DB ContainerEvent rows for replay
3. Fetches Redis log buffer for replay
4. Checks DB lifecycle for terminal state
5. Subscribes to Redis Pub/Sub

New flow:
1. Parse vmid from URL param: `const vmid = parseInt(containerId, 10)`
2. Check Redis creation state: `const creationJob = await getCreationJob(redis, vmid)`
3. If no creation job found:
   - Check if container exists on Proxmox (optional, could just return 404)
   - For simplicity: return 404 with "No active creation found" — the detail page handles viewing existing containers
4. Fetch Redis log buffer: `redis.lrange(getLogBufferKey(String(vmid)), 0, -1)` (same as before, just using vmid key)
5. Check terminal state from Redis: `creationJob.lifecycle === "ready" || creationJob.lifecycle === "error"`
6. Build snapshot from log buffer (parse step events to derive current progress):
   - Instead of building snapshot from DB ContainerEvent rows, parse the Redis ring buffer entries
   - Each entry is a `ContainerProgressEvent` JSON — extract step, percent, scriptNames, etc.
   - This replaces the complex DB event parsing logic
7. If terminal: send snapshot, replay buffered logs, send "done", cleanup
8. If not terminal: send snapshot, replay buffered logs, subscribe to Redis Pub/Sub (same as before)

**Remove imports:**
- `DatabaseService` from `@/lib/db`

**Add imports:**
- `import { getCreationJob } from "@/lib/containers/redis-state"`
- `import { getRedis } from "@/lib/redis"` (or use existing Redis connection pattern)

The snapshot-building logic simplifies significantly because we parse `ContainerProgressEvent`
objects directly from the ring buffer instead of translating from DB `ContainerEvent` objects
with their different field names and metadata format.

**Services Route (`services/route.ts`):**

Currently:
1. Looks up container in DB: `DatabaseService.getContainerById(containerId)`
2. Returns 404 if not found
3. Reads Redis cache: `getCachedServices(redis, containerId)`

New flow:
1. Parse vmid from URL param: `const vmid = parseInt(containerId, 10)`
2. Read Redis cache directly: `getCachedServices(redis, String(vmid))`
3. Return services (or empty array if no cache)
4. No DB lookup needed — if there's a cache, the container exists (or existed recently)

Remove the `DatabaseService` import entirely.
