# Phase 03.6: Remove Container from Database - Context

**Gathered:** 2026-02-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Remove Container and ContainerEvent models from PostgreSQL. Proxmox becomes the sole source of truth for container state. Redis provides ephemeral creation tracking and service/monitoring caching. All container IDs become VMIDs (no more cuid/pve-{vmid} mix).

</domain>

<decisions>
## Implementation Decisions

### Creation progress persistence
- Creation state TTLs in Redis: **24 hours** for active/in-progress, **1 hour** for completed and failed — comfortable window to come back and see results without stale state lingering
- **No dashboard indication** for in-progress creations — progress page is the single place to watch creation
- On reconnect (tab sleep, page refresh), show **step summary + current state** — which steps completed (checkmarks) and the active step, no detailed log replay
- Failed creation shows **error state with failure details only** — no retry button, no pre-filled wizard link; user navigates to wizard manually if they want to try again

### Dashboard loading experience
- **Loading skeletons** while Proxmox data fetches — page shell (header, sidebar, filters) renders immediately via loading.tsx, card-shaped skeletons in the grid
- **Split refresh strategy:**
  - Detail page: resource metrics (CPU, memory, network) poll every **1-2 seconds**
  - Dashboard: full refresh every **30 seconds** (same as current)
- **Parallel fetch with per-node timeout, single render** — all nodes fetched in parallel server-side, ~5s timeout per node, skip unresponsive nodes, render once when all complete/timeout
- Empty dashboard (nodes configured but no containers): **minimal text + create button** — "No containers found" with CTA

### Node failure graceful degradation
- Partial node failure: **healthy nodes render + dismissible error banner** — "Unable to reach Node X — some containers may not be shown"
- Container detail page when node unreachable: **clean error page** — "Unable to reach node X" with back-to-dashboard navigation
- Lifecycle action failure (timeout, transient error): **toast error, no automatic retry** — red Sonner toast with error message, user clicks action again if needed
- All nodes unreachable: **empty dashboard layout with error banner + settings link** — not a full error page, user can still navigate to settings

### Service & credential data lifecycle
- Service monitoring data cached in **Redis with manual refresh** — "Refresh services" button + "last checked" timestamp shown to user
- Service cache TTL: **24 hours** — auto-expires, next view after expiry triggers fresh check
- Credentials: **live fetch only, never cached** — SSH into container on demand when user clicks "Show Credentials", no secrets stored in Redis
- First visit with no cache: **auto-fetch** — Services tab triggers automatic discovery with loading state, then caches result; manual refresh for subsequent updates

### Claude's Discretion
- Redis key patterns and data structures for creation state and service cache
- Exact loading skeleton design and layout
- Error banner component styling and dismiss behavior
- Per-node timeout value (recommended ~5s)
- Resource polling implementation (detail page 1-2s interval)
- Service discovery SSH/pct exec implementation details

</decisions>

<specifics>
## Specific Ideas

- Split refresh is important: resource metrics need near-real-time updates (1-2s) on the detail page, while the dashboard list view is fine with 30s refresh
- Credentials must never touch Redis — always fetched live from the container filesystem via SSH
- Creation progress is a transient "watch it happen" experience, not a historical record

</specifics>
