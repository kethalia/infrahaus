# Plan 13-03: Infra Docs Cross-Linking

## Goal

Add "Deploy via Dashboard" or "View in Dashboard" callout links to the existing MDX docs for each infra service, pointing to `/templates` (for LXC-deployable services) or `/infra` (for docker-compose/GPU services) so docs pages connect back to the live dashboard.

## must_haves

- [ ] `apps/dashboard/content/docs/deployment/dokploy.mdx` contains a Fumadocs `<Callout>` linking to `/templates` (the LXC template for Dokploy)
- [ ] `apps/dashboard/content/docs/networking/wireguard.mdx` contains a Fumadocs `<Callout>` linking to `/templates` (the LXC template for WireGuard Proxy)
- [ ] `apps/dashboard/content/docs/ai/index.mdx` contains a `<Callout>` linking to `/infra` (browse all infra services from the dashboard)
- [ ] `apps/dashboard/content/docs/media/jellyfin.mdx`, `gaming/index.mdx`, and `blockchain/lukso-node.mdx` each contain a `<Callout>` linking to `/infra`
- [ ] `NEXT_SKIP_TYPE_CHECK=1 pnpm --filter dashboard exec next build` completes without MDX parse errors (OOM kill of the TypeScript worker is pre-existing and non-blocking per STATE.md)

<task id="13-03-01" title="Add dashboard deploy callout to dokploy.mdx">
<context>Dokploy is LXC-deployable via the template created in Plan 13-01. The callout should appear near the top of the page (after the Overview section, before Prerequisites) to make the deploy path immediately visible. Fumadocs supports a `<Callout>` MDX component with a `type` prop ("info", "warn", "error"). The callout links to `/templates` with a note that the dashboard can deploy Dokploy as an LXC container.</context>
<steps>

   ```mdx

     **Deploy via Dashboard** — Dokploy is available as a one-click LXC template.
     Go to [Templates](/templates) in the dashboard and click "Discover Templates" to find the Dokploy template.
     You can also [browse all infra services](/infra) from the Infra catalog.
   </Callout>
   ```
3. Verify the import statement is placed at the top of the MDX file (below the frontmatter `---` block), not inline in the body — Fumadocs MDX requires imports at the top of the file
4. Confirm the existing frontmatter (`title`, `description`) is unchanged
</steps>

<context>After all MDX edits, run the Fumadocs-aware Next.js build to confirm no MDX parse errors. The key check is that no MDX syntax errors are reported before any OOM kill.</context>
<steps>
1. Run `NEXT_SKIP_TYPE_CHECK=1 pnpm --filter dashboard exec next build` from the repo root
2. Check the output for MDX parse errors — look for lines containing "Error" related to the modified `.mdx` files
3. If any MDX parse error appears, fix the syntax in the relevant file (common issues: missing closing JSX tags, malformed import statements in MDX frontmatter vs body)
4. The build may be OOM-killed (exit 137) after compilation — this is pre-existing and non-blocking per STATE.md
5. Optionally, also run `pnpm --filter dashboard exec tsc --noEmit` to verify no TypeScript errors were introduced
</steps>
